## 1. Introduction

This register is derived exclusively from acknowledged limitations and known-issue
statements recorded in [`project-management/DECISIONS.md`](../DECISIONS.md). It is **not**
exhaustive: it captures only those risks that have a traceable origin in a specific
DECISIONS.md entry. Risks discovered after this document was written must be appended to
DECISIONS.md first (under a dated entry with a story ID), then added here on the next
update cycle. No row in the table below was invented for this document.

## 2. Risk Table

| RISK-1 | **In-memory consolidation counter not shared across processes.** `MemoryStore.consolidate_every_n` counts `remember()` calls per scope `(agent_id, user_id, thread_id)` in an in-process Python `dict`. Counter resets to zero on process restart. In a horizontally-scaled or serverless deployment with N workers and `consolidate_every_n=5`, each worker fires the inline synchronous Consolidator independently every 5th write *it handles personally* — not globally every 5th write across all workers. Derived memories (SemanticFacts, EntityProfiles) may therefore be created at rates ranging from N× more to N× less frequently than the configured cadence implies. | [`MemoryStore.consolidate_every_n`](../../src/agent_memory_sdk/store.py), [`Consolidator` protocol](../../src/agent_memory_sdk/types.py) | Consolidation may fire more or less frequently than configured in multi-instance deployments; SemanticFacts and EntityProfiles may be created at inconsistent rates across replicas | Medium — any horizontally-scaled or serverless deployment triggers this; single-process deployments are unaffected | Use the out-of-band background-worker pattern (`scripts/consolidate_pending.py` with `consolidated_at IS NULL` polling, per ENH-4) instead of the inline synchronous Consolidator for multi-instance deployments; this is documented in the `MemoryStore` class docstring and in `store.py` | Low if background-worker pattern is used exclusively; Medium if the inline Consolidator is relied upon in a multi-instance deployment | 2026-08-01 — ENH-4: `consolidate_every_n` **"Known limitation"** paragraph: *"the per-scope counter is stored in-memory on the `MemoryStore` instance. It resets to zero on process restart and is **not shared across multiple application instances**"* |
| RISK-2 | **Embedding dimension is baked into the schema at migration time.** The `VECTOR(dim, FLOAT32)` column size for all five memory tables (`working_memory`, `episodic_memory`, `semantic_facts`, `entity_profiles`, `procedural_memory`) is set by the DDL in `0002_memory_tables.sql` at the dimension configured when `MemoryStore` is constructed (default 1536). If the operator later switches to an embedding model that produces a different output dimension, the mismatch between the stored column width and the new provider's vector length will cause Db2 `SQLSTATE 22018` / data truncation errors on INSERT and silently degrade ANN recall on search. Correcting the schema requires a new DDL migration (ALTER TABLE or DROP/recreate the embedding column), recomputation of all stored embeddings from source content, and re-insertion. | All five memory tables, [`repositories/base.py`](../../src/agent_memory_sdk/repositories/base.py) (`EMBEDDING_DIM`), [`db/migrations/0002_memory_tables.sql`](../../src/agent_memory_sdk/db/migrations/) | Embedding-model upgrades that change output dimension are a breaking schema change requiring a migration and re-embedding all stored rows | Low-Medium — embedding models within a single provider generation are dimensionally stable; risk materialises at provider or generation switch | Default dimension (1536) is compatible with common embedding models; `MemoryStore.__init__` accepts an `embedding_dim` argument that propagates to all repositories, making the override point explicit; schema migration path is documented in DECISIONS.md (Step 2/Step 3 entries) | Medium — operational burden is non-trivial if dimension change is needed on a populated database | 2026-07-30 — Step 2: *"A new migration with an ALTER TABLE or Drop/Create of the embedding column is needed to change the dimension"*; 2026-07-30 — Step 3: *"The DDL value is still 1536; changing the stored dimension requires a new schema migration"* |
| RISK-3 | **`ConnectionPool.pool_size` is a hard concurrency ceiling.** The pool pre-opens exactly `pool_size` ibm_db handles at startup (default 5, capped at 20 by [`connection.py`](../../src/agent_memory_sdk/db/connection.py:196)). Under peak load, callers that call `pool.get_connection()` when all slots are checked out block for up to `DB2_POOL_TIMEOUT` seconds (default 30 s) before `ConnectionPoolExhausted` is raised. There is no dynamic pool growth; adding capacity requires a process restart with a larger `DB2_POOL_SIZE` value. | [`db/connection.py`](../../src/agent_memory_sdk/db/connection.py) (`ConnectionPool`), `MemoryStore` | High-concurrency or bursty-traffic workloads may experience queueing latency or `ConnectionPoolExhausted` failures when the pool is exhausted | Medium-High — any production deployment with bursty traffic patterns; baseline risk at default `pool_size=5` with more than 5 concurrent callers | `pool_size` is configurable via `DB2_POOL_SIZE` environment variable (accepted range 1–20); `DB2_POOL_TIMEOUT` controls the wait-before-raise window; sizing guidance in BENCHMARKS.md / SDD-08 | Low with correct pool sizing relative to expected concurrency; Medium with an under-provisioned pool | 2026-07-30 — Step 1: *"Pool size and timeout are configurable via env vars (`DB2_POOL_SIZE`, `DB2_POOL_TIMEOUT`)"*; 2026-08-02 — EPIC-8 technical-feasibility check: *"pool exhaustion under high concurrency is a capacity/sizing question, not a correctness one"* |
| RISK-4 | **Python-side keyword scoring imposes a CPU/memory scale ceiling on hybrid search.** `PIPE-1` implements hybrid retrieval by (1) over-fetching up to `min(top_k * 4, 800)` candidates from Db2 via `VECTOR_DISTANCE`, then (2) computing token-set intersection and RRF fusion in Python over that candidate set, then (3) slicing to `top_k`. The keyword scoring and fusion happen entirely in the Python process, not pushed down to Db2 as a UDF or `CONTAINS`/`SCORE` expression. CPU and memory overhead of the Python scoring step scale with candidate count (up to 800 rows) regardless of total table size; Db2 parallelism is not leveraged for the scoring phase. The Db2 Text Search Extender (`CONTAINS`/`SCORE`) remains an unconfirmed dependency on the target environment and was explicitly not relied upon. | [`repositories/base.py`](../../src/agent_memory_sdk/repositories/base.py) (`_keyword_tokens`, `_rrf_fuse`, `hybrid=True` search path) | Hybrid search latency and Python-process memory usage scale with the candidate over-fetch count, not with Db2 parallelism; becomes operationally significant at table sizes above ~100 K rows per agent scope | Low at typical deployment scales; becomes Medium above ~100 K rows per agent scope or when hybrid search is called in tight loops | Use vector-only search (`hybrid=False`, the default) for high-throughput paths; a future migration could push scoring to a Db2 UDF or `CONTAINS`/`SCORE` expression if the Text Search Extender is confirmed available — explicitly noted in DECISIONS.md as an upgrade path requiring only a single-file change | Low at typical scales; Medium at very large scales or high hybrid-search call rates | 2026-08-03 — PIPE-1: *"If Db2 Text Search Extender availability is later confirmed… that could replace the Python-side token overlap… That would be a documented upgrade path"*; EPIC-7 backlog 2026-07-31: *"re-attempted to confirm current-version (12.1) status via fresh web research… Same unresolved status"* |
| RISK-5 | **`IngestResolver` triggers one similarity `search()` per message in a batch.** When a real `IngestResolver` is configured and `add_messages()` is called with a batch of N messages, `MemoryStore.remember()` executes the resolver's top-k similarity search once per message — not once per batch. An N-message batch therefore produces N `VECTOR_DISTANCE` queries against Db2 before a single row is written. This is the same hot-path cost as the inline `Consolidator` (also synchronous per `remember()` call), but applied to every message in a conversational batch rather than only to working/episodic writes. The default `NoOpIngestResolver` is special-cased in `remember()` to skip the `search()` call entirely, so callers that have not explicitly configured a resolver incur zero overhead. | [`MemoryStore.remember()`](../../src/agent_memory_sdk/store.py), [`MemoryStore.add_messages()`](../../src/agent_memory_sdk/store.py), [`NoOpIngestResolver`](../../src/agent_memory_sdk/types.py:590) | Latency of `add_messages()` scales linearly with batch size when a real `IngestResolver` is active; at batch size N the call adds N Db2 round-trips before writes begin | Medium — any deployment that combines `add_messages()` with a real `IngestResolver` and batch sizes greater than ~5 messages | Use `NoOpIngestResolver` (the explicit default) for bulk ingestion paths where write-time dedup or merge classification is not needed; reduce batch sizes when the resolver is active; resolver is strictly opt-in and adds zero overhead when not configured | Low with `NoOpIngestResolver` (the default); Medium with an active resolver and large batches | 2026-08-02 — EPIC-8 technical-feasibility check: *"a chatty `add_messages()` batch with a real `IngestResolver` configured will run one similarity search per message… This is pre-existing `PIPE-2` behavior"* |
| RISK-6 | **`ibm_db>=3.2.9` native driver auto-downloads a bundled IBM DB2 clidriver at `pip install` time.** On air-gapped networks, restricted CI platforms, or enterprise environments with outbound-download policies, this download may fail silently or raise an error that blocks installation. On Windows with Python 3.8+, `os.add_dll_directory('<clidriver>/bin')` must be called before `import ibm_db` or the import raises a DLL load error — the SDK handles this automatically only when `IBM_DB_WIN_DLL_DIR` is set in the environment. On macOS ARM64, `ibm_db` pins its bundled clidriver to v12.1.0 and no override is available via the package manager alone. | Installation (`pyproject.toml` dependency `ibm_db>=3.2.9`), [`db/connection.py`](../../src/agent_memory_sdk/db/connection.py:70) (Windows DLL guard) | Installation may fail or require a manual workaround in restricted environments; Windows callers who do not set `IBM_DB_WIN_DLL_DIR` will receive a DLL load error at first `import agent_memory_sdk` | Low in standard cloud or developer environments with outbound internet access; Medium in air-gapped enterprise or regulated environments | Set `IBM_DB_HOME` environment variable to point to a pre-installed full Db2 client to bypass the auto-download; `pyproject.toml` documents this in an inline comment; Windows guard in `db/connection.py` is automatic when `IBM_DB_WIN_DLL_DIR` is set; installation guide should be consulted for restricted environments | Low with `IBM_DB_HOME` workaround and documented installation steps; residual Medium for Windows-first deployments without the DLL dir configured | 2026-07-30 — Step 1 and `pyproject.toml`: *"Set IBM_DB_HOME env var to use an existing full DB2 client instead"*; [`db/connection.py`](../../src/agent_memory_sdk/db/connection.py:9) driver-install note: *"On Windows with Python 3.8+, you must call `os.add_dll_directory('<clidriver>/bin')` before importing ibm_db"* |

## 3. Out-of-Scope Risks

The following risk categories are **not tracked in this register**. They are delegated to
deployment infrastructure, the hosting organisation's security controls, and
operational policies, and are outside the SDK's own code surface:

- **Network transport security** — whether the Db2 TCP/IP connection uses SSL/TLS
  (controlled via `DB2_SECURITY=SSL` and the Db2 server's listener configuration, not SDK
  code).
- **Db2 database access controls** — authentication mechanisms, user privilege grants, row-
  and column-level access control, and audit logging at the Db2 engine layer.
- **Backup and recovery** — point-in-time recovery, tablespace backup scheduling, and RPO/
  RTO targets for the database that backs the SDK's tables.
- **Media-level erasure** — cryptographic key rotation, physical media sanitisation, and
  compliance-grade data destruction beyond what `erase_all(scope)` (PIPE-5) achieves at
  the SQL row level.
- **Compliance certification** — SOC 2, ISO 27001, GDPR processor assessments, and any
  other regulatory certification framework: these are organisational obligations, not SDK
  properties.
